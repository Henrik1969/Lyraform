# Flowmini v0.24 Canonical Type Policy

Authority: binding policy established at the v0.24 frontend boundary and
inherited unchanged by active Flowmini v0.25. The v0.25 implementation still
preserves written type references and does not implement semantic resolution.

## Purpose and boundary

This document defines the canonical primitive type identities and classifies
the other type names currently found in Flowmini. It is binding policy for the
v0.24 frontend boundary.

It does not implement semantic type resolution, alias normalization, type
checking, contract checking, ABI lowering, or runtime storage for the complete
type family. Those are later implementation stages. The raw AST must preserve
the type reference written by the programmer and must not substitute a
canonical name.

The phrase *canonical type* in this document means resolved semantic identity.
Existing AST documents also use *canonical typed payload* to describe the
single authoritative C++ variant payload of an AST node. Those are different
claims: a canonical AST payload can faithfully contain an unresolved or aliased
source type reference.

## Raw-AST rule

The raw AST preserves type references exactly as written, including qualified
name segments, generic arguments, array extents, spelling, and source
locations. For example, `Bool`, `bool`, `int`, and `int64` remain distinguishable
source references in the raw AST.

Semantic analysis later resolves a source reference to a canonical primitive,
prelude alias, library/domain type, refined type, ABI contract type, or a
diagnostic. Raw-AST construction must not perform that resolution.

## Canonical primitive identities

The canonical Flowmini primitive identities are:

```text
bool

int8   int16   int32   int64   int128
uint8  uint16  uint32  uint64  uint128

float16  float32  float64  float128

char8  char16  char32
```

These names state language-level identities. They do not promise that every
identity already has parser validation, literal rules, semantic operations,
ABI mapping, or runtime storage in the present implementation.

`string` is not a scalar primitive. String values belong to a library/domain
type whose element, encoding, ownership, and mutation contracts can be defined
without turning the type into a built-in scalar identity.

## Canonical scalar storage strategy

Flowmini adopts a hybrid scalar representation:

```text
canonical scalar wrapper identity
    verified native storage when exact
    portable fixed-bit carrier or provider fallback otherwise
```

Canonical Flowmini type identity is defined by the language. Native storage is
an implementation strategy and optimization; it is never the definition of a
Flowmini type.

A native representation may back a canonical wrapper only when the
implementation verifies that its width, range, representation, and other
storage requirements exactly satisfy the Flowmini contract. Examples of the
intended selection are:

| Canonical identity | Permitted implementation strategy |
|---|---|
| `int32` | `std::int32_t` when verified as an exact 32-bit two's-complement-compatible representation; otherwise a portable carrier |
| `int64` | `std::int64_t` when verified as an exact 64-bit two's-complement-compatible representation; otherwise a portable carrier |
| `int128` | native `__int128` or another provider only when verified; otherwise a portable 128-bit carrier |
| `float32` | native IEEE-754 binary32 when verified; otherwise a portable carrier/provider |
| `float64` | native IEEE-754 binary64 when verified; otherwise a portable carrier/provider |
| `float16` / `float128` | verified native/provider implementation or portable fixed-bit carrier |

Storage verification alone does not approve host arithmetic behavior. A native
operation may be used only when its behavior also conforms to the separately
approved canonical rules for overflow, rounding, exceptional values,
conversions, and diagnostics. Provider conformance therefore covers operations
as well as representation.

Serialization, hashing, persistence, and cross-backend transfer use a canonical
normalized representation rather than native object bytes. The exact encoding
is a later boundary contract; v0.24 does not invent a persistence format.

Future arithmetic providers may use native scalar operations, portable
implementations, SIMD, CUDA, ASM, or other backends. Each provider must preserve
the same canonical semantics and must not change the identity visible to source
code, semantic facts, or later IR.

This policy establishes the wrapper/provider seam but does not add wrapper
classes, portable arithmetic, provider selection, or scalar normalization to
the v0.24 implementation.

## Prelude and compatibility aliases

The following spellings are not canonical primitive identities:

| Source spelling | v0.24 classification | Provisional semantic direction |
|---|---|---|
| `int` | prelude/compatibility alias | likely aliases `int64` |
| `float` | prelude/compatibility alias | likely aliases `float64` |
| `Bool` | prelude/compatibility alias | aliases `bool` |
| `string` | library/domain type name | not a scalar alias |

The classification is binding. The `int` and `float` mappings remain
provisional until their literal, range, conversion, and portability rules are
approved. This task does not add alias resolution.

Existing executable examples rely heavily on `int` and `Bool`; retaining their
source spellings is therefore a compatibility requirement while the semantic
prelude is designed.

## Library and domain types

Named, qualified, generic, record, and refined types are not made primitive by
being commonly used. Current examples include `string`, `list<int>`,
`array<int>`, `collection.list<int>`, `optional<...>`, `result.Result<...>`,
records, and numerical domain names such as `Integer`, `PositiveInteger`,
`Percent`, and `PortNumber`.

The raw AST represents their written type-reference structure. Later name and
type resolution determines which declaration, library constructor, or semantic
identity each reference denotes.

## Refined types and contracts

A declaration such as:

```flow
type Positive refines int64 {
    invariant value > 0
}
```

defines a future named semantic contract type:

```text
refined type identity
    resolved base type (canonical identity or resolved alias)
    ordered invariants/contracts
```

The refined name is not an alternative spelling of its base. The v0.24 raw AST
preserves the base reference plus ordered, located invariant expression IDs.
Resolution of the base, evaluation of invariants, construction checks, and
contract satisfaction belong to semantic analysis.

## ABI contract types

Names such as `c_int`, `c_long`, `c_ulong`, `c_size_t`, and `c_string` are ABI contract
types, not Flowmini primitive identities. They describe an external interface
whose size, signedness, representation, ownership, lifetime, and platform
mapping are governed by an ABI declaration and the selected target.

Raw AST preserves the ABI type name and declaration syntax. ABI policy and
lowering later resolve it to a target-specific representation. In particular,
`c_long` must not be silently normalized to a fixed Flowmini integer in the raw
AST merely because the current compatibility parser internally bases it on
`int`.

## Current implementation evidence

The current compatibility runtime does not yet hold values for the complete
canonical primitive family. Its general `Value` storage currently contains:

```text
bool
signed 64-bit integer
string
record
list
array
ABI struct
empty (`monostate`) state
```

The established executable parser likewise has literal/expression machinery
for integers, Booleans, and strings, with `int` and `Bool` preinstalled as type
names. Float text is observable in the explicit AST, but float execution is not
a completed runtime capability.

This evidence must not be read as the canonical type policy. It is the narrower
legacy execution surface that later work must reconcile with the policy.

## Required follow-up before full value implementation

Implementing values for every canonical identity requires separate, approved
decisions for:

- exact integer ranges, overflow behavior, conversions, and concrete portable
  carrier encoding;
- the semantic formats and exceptional-value rules of `float16` through
  `float128`, independent of host compiler support;
- the meaning and validity rules of `char8`, `char16`, and `char32`;
- literal typing, suffixes, defaulting, and representability diagnostics;
- equality, ordering, arithmetic, widening, narrowing, and mixed-type rules;
- runtime value representation and the boundary between language identity and
  target/ABI storage.

Until those decisions are approved and tested, the implementation must not
claim complete canonical primitive value support. The immediate v0.24 gate is
lossless raw-AST representation and truthful documentation; semantic identity
and value behavior remain later work.

## Historical v0.23 foundation reconciliation

The v0.23 TokenTree bridge line introduced the architectural note
`Lyraform/Flowcore_type_system_foundation.md` in commit
`de45340cdc1e090666bc0f46330af066a7d11081`. That note is preserved as
historical provenance. Its central distinction remains part of the current
direction:

```text
primitive identity
contract-defined representation and validity
domain-defined semantic or algebraic laws
```

The current policy above carries forward the note's useful constraints on
representation, storage layout, ownership, lifetime, mutation, validity,
encoding, operations, ABI strategy, and lowering strategy. It also carries
forward the rule that semantic or algebraic laws constrain which optimizer
rewrites are legal. The current frontend and downstream boundaries express
these ideas through lossless type references, explicit ABI clauses, structural
origins, semantic reports, and later lowering artifacts; the v0.23 bridge
implementation itself is not reinstated.

Some v0.23 examples are intentionally narrowed by the current binding policy.
In particular, the v0.23 examples of `int256`, `int512`, `uint256`, `uint512`,
`float256`, and `float512` are design possibilities rather than current
canonical identities. The approved primitive list, runtime claims, and future
value-implementation decisions in this document take precedence. Likewise,
`ptr`, `ref`, arrays, slices, numeric domains, and text layouts remain
representation or semantic design examples until their separate contracts and
implementation gates are approved.
