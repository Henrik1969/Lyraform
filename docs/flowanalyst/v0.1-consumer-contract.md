# Flowanalyst consumer boundary contract

Flowanalyst is a semantic-analysis provider. It consumes a FlowMini frontend
bundle and produces semantic evidence. A consumer may be a CLI formatter, IDE,
debugger, AI service, web interface, build orchestrator, or another analysis
tool.

```text
flowmini.frontend_bundle v2
        ↓
flowanalyst.semantic_report v1
        ↓
independent projections
```

## Input rules

Consumers and providers must follow these rules:

1. The input is an immutable `flowmini.frontend_bundle` JSON document.
2. Flowanalyst currently accepts bundle version `2` only. Unsupported versions
   must be rejected explicitly; consumers must not guess compatibility.
3. The embedded AST, SymbolTable, source map, and origin contracts remain the
   authoritative structural data.
4. Symbol IDs and AST arena IDs are valid only within one bundle. They must not
   be cached as identities across separate analyses.
5. `ast_path` is a JSON Pointer into the bundle's embedded AST. A debugger may
   navigate it without reparsing source.
6. Source coordinates are interpreted through the bundle's source map. A
   consumer must not infer filenames or locations from diagnostic text.

Flowanalyst and its consumers must not mutate the input bundle or require
private FlowMini headers, libraries, or implementation details.

## Report rules

The report has format `flowanalyst.semantic_report` and version `1`.

Top-level status is one of:

```text
ok       no blocking diagnostics were produced
error    one or more blocking diagnostics were produced
```

Each diagnostic has a stable `code`, `severity`, human-readable `message`, and
`root_cause` marker. Subject-bound diagnostics additionally provide:

```text
subject.symbol id
provenance.source
provenance.ast_path
provenance.line
provenance.column
region
```

The code and structured fields are authoritative. The message is a projection
default and must not be parsed by consumers.

Consumers should display primary/root-cause diagnostics first and may collapse
related consequences. They must retain access to the complete report for
inspection, automation, and AI reasoning.

Target records are independently scoped. A target with status `sane` may be
considered for partial lowering only after its required dependency closure is
also sane. A rejected or incomplete dependency blocks dependent lowering.

The report may expose `analysis_regions`. A region has a stable identity within
the report, a kind, a status, and `requires` edges to prerequisite regions.
These identities are bundle-local and must not be cached across analyses.
Consumers may use the region graph to group diagnostics, show dependency
context, or schedule independent projections. They must not assume that the
current region kinds are exhaustive.

ABI-aware reports may expose `abi_type_contracts`. Each record is provider
declaration evidence for a named ABI carrier and preserves its `repr`,
`ownership`, `access`, `lifetime`, `nullable`, and `opaque` facts. Consumers may
use these facts for resource validation and diagnostics; they must not treat
them as proof that a foreign provider's implementation is safe beyond the
declared contract and the separate Flowbind/provider checks.

Reports may also expose `lowering_plan` with format `flowcore.lowering_plan`,
version `1`. Its operation identities are report-local and carry source
expression/statement provenance. External-call operations include the exact
provider library, symbol, convention, effect, and carrier signature selected by
semantic analysis. The `text_outcome` operation is a provider-backed, typed
`Outcome<Text,TextFailure>` boundary; its `result_outcome` declaration must
remain serializable and must not contain host pointers. A lowerer must reject
unsupported operation kinds rather than infer behavior from source-unit names.
The reference provider's runtime-local outcome struct is an implementation
detail and must not be copied into this artifact.

## Exit contract

```text
0  report produced and has no blocking diagnostics
1  invalid input, unsupported version, or provider failure
2  valid report produced with blocking diagnostics
```

JSON is written to stdout. Provider failures and usage errors are written to
stderr. Consumers must use the structured report, not stderr text, to interpret
semantic findings.

## Independent debugger obligations

An independent debugger may implement navigation by:

1. reading a diagnostic's `provenance.source`;
2. locating `provenance.ast_path` in the bundle AST;
3. resolving the source coordinate through `source_map`;
4. using `subject.symbol` and SymbolTable origins for semantic context.

It must gracefully handle missing optional fields, unknown diagnostic codes,
and additional report fields. It must not reject a valid report merely because
it cannot render a newer diagnostic kind.
